# SPEC-017 — versioned template admission contract

Status: active

## Intent

Define an owner-controlled, machine-verifiable contract for projects created from `service-template`.

## Requirements

- `AC-17.1`: A versioned JSON policy has a closed normalized file inventory containing path, SHA-256 digest, byte length and Git mode for every immutable baseline file, plus explicit quotas. The canonical policy file is itself a regular, byte-identical `0644` contract member in both the immutable archive and the derived project; its digest excludes only its self-referential `contractDigest` field. The total-project quota must equal the declared immutable bytes, canonical policy bytes, closed manifest and provenance byte budgets, and the separately retained configuration budget, so inventory growth cannot silently consume a generic allowance.
- `AC-17.2`: Contract verification binds the policy version and canonical policy digest to project provenance, rejects malformed provenance, and never approves changed runtime, scripts, hooks, provider/dependency declarations or artifact sources. It rejects links and every non-regular object before excluded-path, inventory, or allowlist treatment; reserved tool directories may be excluded only when their root object is an actual non-link directory, and their contents are outside the project admission inventory. It rejects archives whose compressed size, expanded size, entry count, path depth, member type, member mode, member bytes, or terminal structure exceed the declared limits before reading a member payload. A valid archive ends with exactly two 512-byte zero blocks, followed only by zero padding.
- `AC-17.3`: Only declared service identity and safe metadata/configuration differences are admitted. Each editable manifest field has a closed type, value, size and nested-key rule. `service.json` and `template-provenance.json` use the canonical pretty-JSON bytes emitted by the supported authoring path and have individual closed byte limits before parsing. Arbitrary commands, URLs, secret values, unknown manifest fields, whitespace padding, and local-archive repository URL edits are rejected. A GitHub-derived repository URL is permitted only when it exactly matches approved provenance and also satisfies its declared type, byte-size, and pattern rule.
- `AC-17.4`: A local author-created project remains admissible with the template archive digest. A GitHub-derived identity is required only when provenance says it is GitHub-derived.
- `AC-17.5`: Tests exercise the real template inventory plus valid, altered, forbidden and malformed project fixtures, policy-file byte/mode substitution, typed manifest-container attacks, reserved-name file/directory link denials with truthful platform skips, and archive quota and terminal-structure denials.
- `AC-17.6`: A manual development-candidate prerelease is permitted only from the exact full SHA on protected `develop`, through a separately protected `development-candidate` environment with a protected-branch deployment policy, and only after a read-only provider preflight confirms repository immutable releases are enabled. It publishes the already-bound archive, descriptor, raw contract and `SHA256SUMS` once; it neither enables provider settings nor recreates, overwrites, deletes, or reuses an existing tag. An unknown prior create outcome may recover only after the provider reports an immutable, complete exact tuple: four expected asset names and IDs, target full SHA, prerelease/non-draft state, provider SHA-256 digests, and headerless manual HTTPS downloads through the named GitHub origins (`github.com`, `objects.githubusercontent.com`, `github-releases.githubusercontent.com`, and `release-assets.githubusercontent.com`) whose bytes match `SHA256SUMS`, descriptor, policy, version and source SHA. Every missing, mutable, partial, renamed, digest-mismatched, or download-mismatched release fails closed before another mutation.

## Protected publisher custody clarification (issue #17)

AC-17.6 forbids using any preexisting tag for a new publication, including an orphan tag resolving to the desired source. Read-only recovery of a previously completed immutable exact tuple is permitted; it never resumes a draft or performs another write. Before creation, both release and fixed tag-ref lookup must return absent. The publisher explicitly creates the tag at the full source SHA, proves its fixed API ref (including bounded annotated-tag dereference), creates a private draft, uploads only retained accepted buffers, verifies the complete draft by fixed authenticated asset IDs while private, then makes exactly one publish transition. It verifies the final immutable tuple and headerless public downloads. Partial drafts and unknown outcomes remain retained failures, never deletion, replacement or blind retry.

Every tag, release, asset-upload and publish mutation requires an immediately preceding fresh read of immutable-release configuration, protected develop at the exact source SHA, and the protected environment. These controls are requirements, not permission to invent reviewers, credentials or modify settings. Metadata is limited to 1 MiB raw UTF-8, bounded depth and unique JSON keys; descriptor to 4096 bytes, checksum manifest to 1024 bytes, contract to 128 KiB and archive to the existing contract compressed quota (absolute 256 KiB). Streamed bodies and local file reads stop at their bounds before unrestricted allocation. Requests and body streams share a 30-second deadline. Authenticated requests use exact fixed GitHub API/upload endpoints with manual redirect rejection; downloads have no credentials and allow only bounded redirects to approved HTTPS origins, rejecting userinfo, ports and fragments in every raw redirect authority before URL resolution can normalize them. Network-path authorities follow the same grammar as absolute URLs; ordinary relative path redirects remain permitted.

AC-17.7: Injectable actual fetch/read/write state-machine regressions cover success, read-only recovery, all release/tag collisions, recursive tag cycles/mismatch, protected-policy change before each mutation, retained buffers, private mismatch/nonpublication, API and asset identity, duplicate/raw JSON bounds, stream bounds/stalls, deadlines and credential-free public redirects. Test source remains UNEXECUTED until separate entire source review and fresh complete-input ROOT admission.

The actual publisher validates the held archive buffers with the existing contract/TAR parser before any provider request, against the exact held checked-out owner policy: inventory names, directory set, payload bytes/digests/modes, policy self-member, source PAX syntax, terminal structure and all existing archive quotas. A self-consistent descriptor/checksum substitution is insufficient. The parser is importable without running its standalone project-verifier entrypoint; authoring/provenance/allowed-difference behavior remains unchanged.

## Windows gate and CLI entrypoint requirements (issue #17 review F1–F3)

- `AC-17.8`: Each native command in the actual Windows test and verification helpers must immediately capture and propagate its own nonzero exit before any successor command. Standalone `pwsh -File` and GitHub Actions-style callers must both fail; a later success must never hide an earlier failure. Actual-helper subprocess regressions cover first failure with successor not called, final failure, and both success for both helpers and both caller forms, with the native-error preference explicitly false.
- `AC-17.9`: All three CLIs (workflow validator, private publisher and project verifier) recognize physical entrypoint identity across ordinary/encoded absolute paths, directory aliases and direct script aliases using APIs available on the actual Node baselines. Imports with absent, present unrelated or missing entrypoint argv remain silent and perform no network or CLI work. Actual subprocess regressions require valid workflow success output and invalid nonzero diagnostics, publisher invalid-usage nonzero diagnostics without network authority, verifier argument denial and valid verified output through physical aliases. Windows directory junction coverage remains mandatory; direct file symbolic-link privilege constraints are reported truthfully without weakening other native gates.
- `AC-17.10`: Documentation describes the closed inventory and separate canonical policy member truthfully without hard-coded inventory counts that drift. F1–F3 source and regression changes require a DIFFERENT entire cumulative review and NEW complete-input ROOT admission before execution; publisher custody, all quotas except mathematically closed total growth, deadlines, platform assertions and authoring differences remain unchanged.
